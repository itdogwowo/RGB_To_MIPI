### 2.3 面板（`schlitzblende-main`）

| 項目 | 值 |
|---|---|
| 型號 | Samsung `AMS983JC01F1A`（A1706 Touch Bar） |
| 解析度 | **60 × 2170**，24-bit RGB |
| 介面 | **MIPI DSI，命令模式（command-only）**，video mode 不支援 |
| 關鍵限制 | 用**非標準 `0x3C` 長封包**連續寫像素 → 這就是為什麼需要 SSD2828，不能用 P4 原生 DSI |

### 2.4 為什麼不採用 P4+C61 版（`WT9932P4C61-TINY_SCH_V1.0.pdf`）

| 項目 | 純 P4 版（採用） | P4+C61 版（不採用） |
|---|---|---|
| 模組 | `WT0132P4-A1` | `WT0132P4C61-S1`（88 pin，內含 C61） |
| 引出排針 | **2 × 27 = 54 pin** | **1 × 27（PIN HEADER）+ 1 × 17（C61 flasher）** |
| 可用 P4 IO | **41 條**（扣 TF 卡） | **≤ 28 條**（J4 上約 22 條 + J3 的 IO3–IO7）<br>※此列為上限估計，C61 版未做逐腳匯出 |
| RGB888 需要 | **27 條**（24 data + PCLK + DEN + VSYNC） | 27 條 → **放不下 SPI/RESET** |
| MIPI DSI | 15P FPC（J2） | **17P FPC**（J1） |
| 結論 | ✅ 可跑 RGB888 | ❌ 只能 RGB565 或 SPI 送像素 |

> 這一節是**決策紀錄**：C61 版不是不能做，是「做下去要犧牲色彩深度或改用 SPI 隧道」。
> 若之後要 Wi-Fi，建議走 SPI/SDIO 外掛，而不是換排針介面。

## 7. 連線鐵則（照這個做才不會白做）

1. **線端點必須正好落在 `getAllPinsByPrimitiveId()` 回報的 (x, y)**，線「跨過」腳位不算連接。
2. 每條網路都要 `sch_PrimitiveAttribute.createNetLabel(x, y, net)` 命名；同名才合併。
3. **`createNetLabel` 一定會長出一條 30 單位 stub**，stub 末端沒有腳 → 這就是 DRC 的 `SHOWDANDLING`。
   **所以「標籤式的網路」天生會有一筆警告**；要真的歸零，只能讓網路至少接到**兩個腳**（S1 的做法）。
4. 改磁碟上的 `.esch2` 編輯器不會重讀（`chokidar degraded`）→ **一律走 `/execute`**。
5. 動完 `save()` 等 8 秒再跑 DRC。
6. 每次重排後用 `getNetlistFile()` 逐腳 diff，`lost/added` 必須空。

### 14.2 統一 Value 的兩個坑

**坑 A：直接改 `Name` 會觸發 `ATTRMATCHCODE`**

我原本用 `sch_PrimitiveComponent.modify(id, { name: '10uF' })` 把 C11/C12/R4/R12/R13/R14 的顯示名改掉，

| 焊盤 / 孔 | 1.6 mm 方盤 / **1.05 mm 孔** |

### 19.3 做法：整片 y 鏡像 + J6/J7 對調

**為什麼是「y 鏡像」**：翻面安裝 = 板子沿水平軸翻過去，數學上就是 `y → H − y`。
**x 不動** → pin 1 仍在左邊 → 翻面後 pin 1 還是對 pin 1（不會變 pin 27）。

| 動作 | 內容 |
|---|---|
| 板框 | 70 × 32 → **69.000 × 28.000**（與 P4 同尺寸，數值直接照抄） |
| 全部 39 顆 | `y → 28 − y`（剛性反射，相對距離全部保留，所以間距不會變差） |
| **J6** | → y = **1.2847**（**下排**） |
| **J7** | → y = **26.6847**（**上排**） |
| 排針 x | 35.0 → **34.4001**（照 P4） |

> 因為翻面後「CAD 的下緣」會變成「實際安裝的上緣」，所以 **J6 必須放到 CAD 下排**
> 才會在裝上去之後對到 P4 的 J6。這就是你要的「上下排針反轉」。

## 20. RGB 配對再修正：翻面後最佳解變回原順序（2026-10-28 01:25）

> **§18 的結論已被本節取代**：§18 的反轉配對是「翻面之前」的最佳解，翻面後最佳解變回原本順序。

### 20.1 為什麼會反覆

| 時間點 | 板子狀態 | 最佳配對 | 總長 |
|---|---|---|---|
| §18（翻面前） | J6 在上排、U1 在 y=16 | **反轉**（DATA0→J6.21） | 414.1 mm |
| §19（翻面後） | J6 在下排、U1 在 y=12 | **原順序**（DATA0→J6.1） | 432.6 mm |

翻面（`y → 28 − y`）把 U1 與 J6 的相對位置顛倒了，所以最佳配對也跟著回到原順序。

### 20.2 還發現一件事：U1 是 rotation 180°

| 元件 | 旋轉 |
|---|---|
| U1（SSD2828 QFN-68） | **180°** |
| 其餘 38 顆 | 0° |

180° 對這個設計**反而是好的**：U1 的 24 根 DATA 腳落在**下緣**，正對下排的 J6（21 條資料線），
而 DSI 4 根落在上緣。若轉回 0°，24 條資料線會全部朝上、離 J6 更遠。

> **這也是 §18 判斷錯誤的根源**：當時我用的是 U1 未旋轉的座標。

### 20.3 做法：把 §18 的反轉改回原順序

同樣用「先改暫存名 `TMPn` → 再改終值」＋**每筆存檔**（見 §18.4 的坑）。

| 結果 | 值 |
|---|---|
| 原理圖 DRC | **0** |
| 配對 | DATA0=**IO15** … DATA20=**IO45**、DATA21–23=IO16/17/18 |
| PCB 是否同步 | `importChanges()` **這次成功了**（第一次失敗，見 §17.2） |

### 20.4 交叉驗證

| 檢查 | 結果 |
|---|---|
| J6 的 21 條資料線 x 座標 | **完全單調遞增 → 無交叉** ✅ |
| 總線長 | **432.6 mm**（反轉版 500.4 mm，改善 13.6%） |
| 單腳網路 | 0 |
| 最長線 | `DATA21→J7.1` 40.0 mm（見 §20.5） |

### 20.5 剩下 3 條偏長（結構性限制）

`DATA21–23` 必須走 J7.1–3，但 **J7.1–3 在板子最左端**（x=1.4 mm），
而 U1 的 DATA21–23 在它右緣（x≈38 mm）→ 40 mm 的斜拉。

這是因為 J6 只引出 21 根可用 IO，剩下 3 根只能落在 J7.1–3。
除非把 U4 用的 3 根（IO40/41/42）換掉，否則無解。

我對 U1 的位置做了網格掃描（2 mm 步進，每個位置都跑一次最佳配對）：

|---|---|---|
| **(34, 12) 目前** | **432.6 mm** | 目前就是最佳 ✅ |
| (24, 8) | 339.0 mm | 要改 **16 條** |

## 21. 去耦電容 C3–C6 移到 U1 電源腳旁（2026-10-28 21:30）

### 21.1 為什麼要做

你問「是不是放一堆就好」——不行。原因是**走線電感**（約 1 nH/mm）會蓋掉電容的阻抗：

| 電容離腳 | 走線電感 | 100 MHz 阻抗 | 效果 |
|---|---|---|---|
| 2 mm | 2 nH | 1.26 Ω | 可用 |
| 5 mm | 5 nH | 3.14 Ω | 變差 |
| **22 mm（C5/C6 原本）** | 22 nH | **13.8 Ω** | **等於沒接** |

100 nF 本身在 100 MHz 只有 0.016 Ω，但 22 mm 走線就是 13.8 Ω——**走線比電容大 860 倍**。

### 21.2 移動前後（實測焊盤距離）

| 電容 | 原本位置 | 原本到 3V3 腳 | 新位置 | **現在到 3V3 腳** | 到 GND 腳 |
|---|---|---|---|---|---|
| C3 | (32.85, 17.92) | 6.1 mm | **(35.8, 16.9)** | **3.76 mm**（pad 16） | 2.93 mm（pad 17） |
| C4 | (32.85, 11.35) | 5.4 mm | **(35.6, 4.6)** | **3.08 mm**（pad 33） | 3.10 mm（pad 32） |
| C5 | (14.56, 14.3) | **23.0 mm** | **(43.0, 17.2)** | **4.39 mm**（pad 68） | 3.29 mm（pad 3） |
| C6 | (14.31, 6.33) | **22.1 mm** | **(46.4, 16.6)** | **3.59 mm**（pad 68） | 4.64 mm（pad 67） |

C5/C6 從 **22 mm 降到 3.6–4.4 mm**，效果差別是「完全無效」變成「可用」。

### 21.3 施工過程（含兩次微調）

| 步驟 | 結果 |
|---|---|
| 第一次放 (36.8,16.6) / (36.2,5.4) | DRC **3 筆**：C4 撞 U1_35/36、C3 撞 Y1_1 |
| 微調到 (35.8,16.9) / (35.6,4.6) | DRC **0**（跨元件） |

### 21.4 還不完美的地方

| 問題 | 說明 |
|---|---|
| **U1 pin 64 沒有專屬電容** | C5/C6 最近的都是 pad 68。64 與 68 相距 1.6 mm，共用還算可以，但不是一腳一顆 |
| **右側空間不足** | U1 焊盤右緣到 C7–C10（x=47.85）只剩 **1.65 mm**，塞不進一顆 1.6 mm 的 0603 |
| **2 層板沒有 GND 平面** | 電容的 GND 迴路只能走線，實際效果比上面算的再差一些 |

**建議**：若要在 pin 64 也補一顆，必須把 C7–C10 往右挪約 2.5 mm（會讓 1V2 去耦從 3.6 mm 變成 6.1 mm）。這是取捨，不是對錯。

## 24. 存檔危機與修復（2026-10-30 00:40–01:30）

### 24.1 事件

| 時間 | 現象 |
|---|---|
| 00:33 | 檔案寫入（1,081,908 bytes） |
| 00:48 | `pcb_Document.save()` 回 **false**，磁碟上 **0 條走線** |
| 00:49 | 逐筆檢查 → **3396 條 LINE 與 205 個 VIA 的內容全是空的**（`{...}|||`） |
| 01:00 | 對照健康檔（口袋板 PCB）→ 該檔 0 條空 body |

**根因**：自動佈線（WASM 引擎）產生的圖元是**預覽物件**，
`save()` 會回 `true` 但**序列化時把它們丟掉**——所以「存了」等於「沒存」。
log 裡那四筆 `[object WebAssembly.Exception]` 就是引擎崩潰的證據。

### 24.2 搶救

在刪除/重建之前，先用 API 把記憶體裡的佈線**完整匯出成 JSON**：

- `docs/refs/pcb_routing_rescue.json` —— **746 段走線 + 95 個過孔**，含精確座標、層、線寬

### 24.3 重建（把預覽物件變成真圖元）

| 步驟 | 內容 |
|---|---|
| 1 | 刪掉全部舊走線（含無法序列化的預覽物件） |
| 2 | 用 `pcb_PrimitiveLine.create` / `pcb_PrimitiveVia.create` **重新繪製** |
| 3 | 順手修正：移除 15 段零長度退化段、**3 個 90° 轉角倒成 45°** |
| 4 | 存檔 → **成功寫入磁碟**（1,377,046 bytes） |

> `pcb_PrimitiveVia.create` 的簽名是 `(net, x, y, holeDiameter, diameter)`，
> 第 6 個參數是 `viaType` 列舉——傳 `false` 會失敗（我一開始就踩到）。

### 24.5 曾試過但回退的改動

把電源線從 7.6–10 mil 加粗到 16 mil → **232 筆間距違規**。
因為自動佈線是以 7.6 mil 的間距排的，加粗後塞不下。
**已回退**，電源線寬維持原值；要正確加粗必須重佈那 286 段。

### 24.6 唯一還沒佈的區域：J1

用「焊盤是否有銅連接」逐顆檢查：**271 個焊盤中有 54 個沒有任何銅**，
而且**全部集中在 J1（螢幕 DF40 接頭，30 個焊盤）**。其餘 217 個都接好了。

| J1 腳 | 網路 | 另一端 |
|---|---|---|
| 3 / 5 | D_CLK_P / D_CLK_N | U1.7 / U1.8 |
| 9 / 11 | D_DATA_P / D_DATA_N | U1.1 / U1.2 |
| 6 / 4 / 12 / 10 | D_TE / D_VSYNC / D_RST / D_INT | U4.3 / U4.4 / U4.1 / U4.5 |
| 21 / 23 | D_SCL / D_SDA | R2.1 / R3.1 |
| 18/20/22、15/17 | 3V3、1V8 | 電源 |
| 1,2,7,13,14,16,19,24–30 | GND | 平面 |
| 8 | $1N9 | R1.1 |

**為什麼自動佈線跳過它**：J1 在板子最左（x≈318 mil），
而 DSI 的對端 U1 在 x≈1834 mil —— **要橫跨 38 mm**，穿過整個擁擠區。

這是 §22.6 早就標記過的擺位問題：**J1 離 U1 的 DSI 腳太遠**。

### 24.7 建議（二選一）

| 方案 | 做法 | 效果 |
|---|---|---|
| **A（推薦）** | 把 J1 移到 U1 上方偏左（約 x 26–30、y 20–22） | DSI 從 38 mm 縮到 ~10 mm，自動佈線一次就過 |
| B | 保持 J1 位置，手動拉那 17 條 | 需要繞過整片已佈線區，很難 |

搬完 J1 再跑一次自動佈線，剩下的就是補 GND / 電源鋪銅。

**內層零走線** —— 這一點成功了（第一次自動佈線時 Inner1/Inner2 各有 130/92 段訊號）。

### 25.2 存檔危機重演（同樣的 bug）

自動佈線跑完後：`save()` 回 **false**，磁碟上 **0 條走線**（只有 2 個鋪銅框）。
與 §24 完全相同的成因：**WASM 自動佈線產生的圖元無法序列化**。

**這次的解法（可重複使用）**：

| 步驟 | 指令 |
|---|---|
| 1 | 用 API 把記憶體幾何匯出 → `docs/refs/pcb_routing_rescue_v2.json`（757 段 + 107 過孔） |
| 2 | `dmt_EditorControl.closeDocument(tabId)` 關掉 PCB 分頁（幽靈圖元一併消失） |
| 3 | `openDocument(pcbUuid)` 重開 → 從磁碟載入（0 走線、2 鋪銅框保留） |
| 4 | 逐段 `pcb_PrimitiveLine.create` + `pcb_PrimitiveVia.create` 重畫 |
| 5 | `save()` → **true**，磁碟確認為 742 段 / 107 過孔 / 56 網 |

> **關鍵**：`closeDocument` + `openDocument` 是清掉「存不進去的幽靈圖元」唯一可靠的方法。
> 對幽靈圖元呼叫 `delete()` 會回 `true` 但**完全無效**。

### 25.3 鋪銅為什麼沒有銅箔

`pcb_PrimitivePour.create()` 可以建立覆銅**框**（net + layer 正確、可存檔），
但 `rebuildCopperRegion()` 回 `undefined`，`pcb_PrimitivePoured` 數量為 0。

官方文件已註明：

> 当前版本在纯 API 创建的覆铜上重建会报内部错误

→ **銅箔必須在 GUI 執行一次「重建覆銅」**。
